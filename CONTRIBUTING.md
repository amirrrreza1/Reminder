# Contributing to Reminder

Thank you for helping build a small, reliable, self-hosted reminder system. This project values explicit behavior, focused changes, respectful review, and tests for calendar/notification edge cases.

## Project stage

Phase 1 foundation is in place. Use the workflow below for local development. Feature work should still reference requirement IDs in [docs/PRODUCT_SPEC.md](docs/PRODUCT_SPEC.md).

## Before opening an issue

- Search existing issues and the roadmap.
- Read the relevant product, architecture, data, API, design, deployment, or testing section.
- Do not post secrets, real reminder content, provider payloads, database dumps, or private logs.
- Report vulnerabilities through [SECURITY.md](SECURITY.md), not a public issue.

Good bug reports include:

- requirement ID or documented behavior;
- minimal reproduction with synthetic data;
- expected and actual result;
- app release/commit, browser, Docker/Compose, and PostgreSQL versions;
- redacted logs using internal request/delivery IDs only.

Feature proposals explain the user problem, why it fits the product’s narrow surface, and effects on calendar semantics, schema/migrations, API, privacy, operations, accessibility, and documentation.

## Development setup target

Prerequisites: current LTS Node.js, Corepack/pnpm, Docker with Compose v2, and Git.

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env
docker compose up -d db
pnpm db:migrate
pnpm dev
```

The worker should run in a second terminal during notification work:

```bash
pnpm dev:worker
```

Use fake SMTP/Telegram services for local automated work. Never reuse personal or production provider credentials in tests.

## Architecture boundaries

- Pure recurrence, calendar, eligibility, and money logic belongs in `packages/domain`.
- Database schema/repositories/migrations belong in `packages/db`.
- Provider-specific behavior stays behind adapters in `packages/notifications`.
- Route handlers validate and call services; they do not contain recurrence math or send providers directly.
- Client components never import database, worker, environment, or provider modules.
- Raw SQL is welcome when it makes PostgreSQL constraints/locking clearer; accompany it with integration tests.

## Coding standards

- TypeScript strict mode; avoid `any` and unsafe assertions.
- Prefer small, named domain functions and discriminated unions.
- Parse untrusted input once at the boundary and keep validated types inside.
- Store user content as plain text and escape at every output context.
- Use UTC instants plus explicit local calendar/timezone semantics; never depend on host-local defaults.
- Represent money as integer minor units; never use floating-point arithmetic.
- Use semantic design tokens/components rather than arbitrary one-off UI values.
- Preserve logical CSS properties and keyboard/RTL behavior.
- Do not add runtime telemetry, remote fonts, or new outbound services without an approved specification change.

## Database changes

Every database pull request includes:

- a named, checked-in SQL migration;
- schema/repository changes;
- constraint/index rationale;
- migration test from the previous-release fixture;
- backup/rollback/compatibility note;
- updated data/API/deployment documentation where applicable.

Never use schema push as the production migration path. Do not edit an already released migration; add a new one.

## Tests

Target checks:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm test:integration
pnpm test:e2e
pnpm build
docker compose build
```

See [docs/TESTING.md](docs/TESTING.md) for critical fixture, concurrency, accessibility, visual, provider, backup, and release obligations.

A behavior change is incomplete without tests. Expected calendar values must not be generated by the same code/library under test.

## Commits and branches

- Branch from the current default branch.
- Use a focused name such as `feat/jalali-recurrence` or `fix/expired-lease`.
- Prefer [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) such as `feat(worker): add delivery lease recovery`.
- Keep mechanical formatting/dependency churn separate from behavior when practical.
- Rebase or merge the latest default branch according to maintainer guidance; never force-push another contributor’s branch.

## Pull requests

A good pull request:

- solves one coherent problem;
- links its issue and requirement IDs;
- explains user-visible behavior and tradeoffs;
- lists tests and manual verification;
- calls out schema, environment, security, accessibility, provider, or operational impact;
- updates documentation, `.env.example`, and changelog when applicable;
- contains no unrelated refactor or generated noise.

Checklist:

- [ ] Scope matches an issue/specification or the specification was updated.
- [ ] Unit/integration/component/E2E coverage is appropriate.
- [ ] Calendar expected values are independently grounded.
- [ ] Database migration and compatibility notes are included if needed.
- [ ] UI keyboard, screen-reader, responsive, reduced-motion, and RTL implications were checked.
- [ ] Error/log paths redact secrets and personal content.
- [ ] New dependency is necessary, maintained, licensed compatibly, and pinned through lockfile.
- [ ] Documentation, environment template, and changelog are current.
- [ ] No real credentials or personal data appear in commits, fixtures, screenshots, traces, or logs.

## Review expectations

Maintainers review correctness, scope, clarity, tests, accessibility, operations, security, and documentation. A requested change is about the contribution, not the contributor. Authors should expect extra scrutiny around recurrence math, migrations, concurrency, external messages, and secret handling.

Approval does not authorize merging when required CI or release gates fail. Maintainers may close proposals that expand the product beyond its stated non-goals without a convincing specification change.

## Documentation changes

Documentation-only contributions are valuable. Keep requirement IDs stable; mark removed requirements as superseded rather than silently reusing an ID. Validate relative links and code examples. Do not claim an implementation or command works until it is tested in the repository.
